# Fix 2-Player Multiplayer — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Fix the 2-player (white vs black via WebSocket) game flow so two human players can actually play a full game.

**Architecture:** The current design has a fundamental flaw — each WebSocket `GameConsumer` creates a private in-memory `BackgammonEngine` at connect time and never reloads from the database. This means Player A's engine never sees Player B's opening roll, moves, or state changes. The fix: reload engine state from DB before every action, or switch to a single engine-per-room pattern. This plan uses the **reload-before-action** approach (minimal refactor, no cross-consumer shared state).

**Tech Stack:** Django 5 + Channels 4 + Daphne + SQLite (backend); React 19 + Vite (frontend)

---

## Root Cause Analysis

### The Core Bug: Stale In-Memory Engine

Each `GameConsumer.connect()` loads state from DB into `self.engine` once. Every subsequent handler (`handle_roll_dice`, `handle_move`, etc.) operates on this stale in-memory copy. It is never refreshed from DB after another player's consumer writes to it.

**Concrete failure trace:**
1. Player A (white) connects → `engine_A` loaded from DB
2. Player B (black) connects → `engine_B` loaded from DB
3. Player A rolls opening die → `engine_A.state.openingRoll.white = 4`, saved to DB
4. Player B receives broadcast, but `engine_B` has `openingRoll.white = None` still
5. Player B rolls → `engine_B.apply_opening_roll` detects both rolled, sets `phase = 'moving'`, saves to DB, broadcasts state_update
6. Player A's frontend gets the correct state via broadcast (UI looks correct)
7. Player A clicks to move → `engine_A.make_move()` runs on stale engine: `phase` is still `'opening_roll'`, `dice` is empty → `'Invalid move'` → **game is stuck**

### BUG 1: Empty Board in `get_initial_state()`
`backend/game/engine.py:15` returns `p = [0] * 24` — no checkers on the board. The frontend engine has `initialBoard()` with the full starting setup, but the backend starts empty.

### BUG 2: Second Player Never Gets Board State
When User B joins via REST and connects via WebSocket, `get_game_state()` does `get_or_create` which creates a `GameState` with `state_data = {}` (empty dict). The connect handler checks `if not game_state.state_data:` which is `not {}` = `True`, so it calls `get_initial_state()` — the **empty board** bug again.

### BUG 3: `roll_dice()` Doesn't Clear `dice` on Auto-Skip
When a player rolls and has zero legal moves, line 164-165 clears `remaining` but NOT `dice`. This means the frontend's `canRoll` check (`dice.length === 0`) returns false → Roll button stays disabled forever.

### BUG 4: Race Condition on `join_room`
No transaction isolation. Two simultaneous join requests for the same room could both set `black_player` (last writer wins).

### BUG 5: Inconsistent Error Messages (Hebrew/English)
Engine uses Hebrew for turn messages (`'תור לבן'`) and English for errors (`'Not your turn'`). The README and project conventions say English UI.

### BUG 6: Match Scoring Not Wired
`GameRoom.white_score` / `black_score` exist but are never updated. The game-over flow doesn't send `game_finished` event, doesn't update scores, doesn't show a result overlay for multiplayer matches.

---

## Proposed Fix

**Approach: Reload engine state from DB before every action.**
- In every consumer handler that mutates state, call `self._reload_engine()` first to sync the in-memory engine from the DB.
- This is the minimal safe fix — no cross-consumer shared state, no async locks, no Channels layer re-architecture.
- After mutation, `_save_and_broadcast()` writes back to DB (already implemented).

**Why not a single shared engine?** That would require in-memory state shared between consumer processes, which doesn't work with Daphne's multi-process model and would break if the server restarts. The DB is the source of truth.

**Important:** `transaction.atomic()` on a `@api_view` may interact with DRF's auto-handling. The safer approach is to use `transaction.atomic()` inside the function body, or wrap only the sensitive reads/writes.

Simplest safe version:

```python
@api_view(['POST'])
def join_room(request):
    code = request.data.get('code', '').upper().strip()
    user = request.user
    with transaction.atomic():
        rooms = list(GameRoom.objects.select_for_update().filter(code=code, status='waiting')[:1])
        if not rooms:
            return Response({'error': 'Room not found or already full'}, status=status.HTTP_404_NOT_FOUND)
        room = rooms[0]
        if room.black_player is not None:
            return Response({'error': 'Room is full'}, status=status.HTTP_400_BAD_REQUEST)
        if room.white_player == user:
            return Response({'error': 'You are already in this room'}, status=status.HTTP_400_BAD_REQUEST)
        room.black_player = user
        room.status = 'playing'
        room.save()
    # ... return Response outside atomic to keep the transaction short
```

```python
async def handle_move(self, payload):
    await self._reload_engine()
    result = self.engine.make_move(
        payload.get('from'), payload.get('to'), self.player_color
    )
    if not result.get('success', False):
        return await self._send_error(result.get('message', 'Invalid move'))
    await self._save_and_broadcast('move_made', self.engine.state)

    # Check if game just finished
    if self.engine.state.get('phase') == 'game_over':
        await self._handle_game_over()
```

**Step 2: Add `_handle_game_over()` method**

```python
async def _handle_game_over(self):
    winner = self.engine.state.get('winner')
    win_type = self.engine.state.get('winType', 'single')
    cube = self.engine.state.get('cube', 1)
    base = 1 if win_type == 'single' else 2 if win_type == 'gammon' else 3
    points = base * cube

    room = await get_room(self.room_id)
    if room:
        if winner == 'white':
            room.white_score += points
        else:
            room.black_score += points
        await database_sync_to_async(room.save)()

    await self.channel_layer.group_send(
        self.room_group_name,
        {
            'type': 'game_message',
            'event_type': 'game_finished',
            'payload': {
                'winner': winner,
                'winType': win_type,
                'points': points,
                'cube': cube,
                'whiteScore': room.white_score if room else 0,
                'blackScore': room.black_score if room else 0,
            },
            'playerColor': self.player_color,
        }
    )
```

**Step 3: Also handle double-decline game over**

In `handle_respond_double`, check for game-over after double is declined:

```python
async def handle_respond_double(self, payload):
    await self._reload_engine()
    result = self.engine.respond_to_double(
        payload.get('accept', False), self.player_color
    )
    if not result.get('success', False):
        return await self._send_error(result.get('message', 'Invalid double response'))
    await self._save_and_broadcast('double_response', self.engine.state)
    if self.engine.state.get('phase') == 'game_over':
        await self._handle_game_over()
```

## Risks and Open Questions

- **Redis for channel layers**: Currently using in-memory channel layer (Channels default). For production, needs Redis. Fine for dev.
- **`_reload_engine()` adds DB query per action**: Adds ~5-10ms latency per action. For a turn-based game this is negligible. If it becomes a problem, cache the state in-memory and use a version counter.
- **`select_for_update()` on SQLite**: SQLite supports row-level locking but with limited concurrency. Fine for dev. PostgreSQL recommended for production.
- **Match scoring**: Only wired for the first game in a session. Rematch/next-game flow is not implemented — the `handleNextGame` callback doesn't trigger a new WebSocket sequence. This is a known gap for Phase 2.
- **Frontend tests**: `vitest` needs to be configured. Run `pnpm add -D vitest && pnpm vitest run` to verify it works.
