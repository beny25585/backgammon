## הפעלה

### commit ופקודה אחת

אחרי commit ידני בכל מאגר ששונה, מריצים את אותה פקודה בכל פעם:

```powershell
.\PUBLISH_AND_DEPLOY.ps1
```

המסלול הרגיל כולל בדיקות כלי הפריסה, בדיקות ובניות של שלוש החזיתות,
בניות Docker ובדיקות שרתי Django והקוביות, push לארבעת המאגרים,
אימות ומשיכת המקורות המדויקים בשרת, גיבוי ועדכון פרודקשן.
בדיקות כלי הפריסה משתמשות בשירותים מדומים; ההודעות המדומות שלהן
נשמרות בנפרד מפלט הריצה החיה ומוצגות במקרה כשל בבדיקות הכלי.

לפני העבודה הארוכה נבדק השרת באמצעות SSH: פרודקשן רשום ופתוח,
ללא ריצת פריסה מקבילה, ללא משחקים פעילים וללא מסירות ממתינות.
כשיש חסימה מוצגים קודי החדרים או מוני המסירה. אין ביטול משחקים,
הכרעה או מחיקת מסירות אוטומטיים. SSH ו־sudo ממשיכים להשתמש בהרשאות
ובסיסמאות הקיימות; הסקריפט אינו משנה את מנגנון האימות.

לאחר תקלה פותרים את הבעיה ומריצים **אותה פקודה**. אין צורך לבחור
מזהה הרצה או להעתיק סקריפט Python מיוחד לתקלה. מנגנון ההמשך החדש
משתמש רק בקבלות בעלות progress.json בגרסת התהליך הנוכחית, עם אותם
ארבעת commits ואותם hashes של הכלי והגדרות הבדיקה. ריצות היסטוריות
ללא קבלה זו אינן נבחרות אוטומטית. שינוי commits מבטל את ההמשך הכללי;
מיחזור חזיתות שלא השתנו נבדק בנפרד לפי הכללים המעודכנים למעלה.

הכלי שומר שלבים שהסתיימו בשלמות: בדיקות הכלי, כל חזית בנפרד, קבוצת
התמונות, כל שרת Django בנפרד ובדיקות הקוביות. שלב שנכשל באמצע אינו
מסומן כמושלם. לוגים ותוצאות נבדקים לפי SHA256, וההוכחות מועתקות לקבלה
חדשה ללא שינוי הקבלה המקורית. שרשרת ההמשך שומרת גם שלבים שעברו לפני
תקלה מוקדמת בהרצה חוזרת. שינויים בגרסת Node/pnpm או בסביבת Docker,
בתמונות היישומים או בתמונות PostgreSQL/Redis של הבדיקות מונעים שימוש
בהוכחות שאינן מתאימות לקלטים הנוכחיים.

מזהי התמונות נשמרים מהתוצאה של docker image inspect, ולא בהנחה
ש־config digest בלוג הוא מזהה Docker. כל מזהה משויך ללוג הבנייה שלו,
למקור ולהרצה שהפיקו אותו. תמונה חסרה נבנית מחדש; בדיקות שתלויות
במזהי התמונות החדשים רצות שוב. תוויות או הוכחות שהשתנו עוצרות את ההמשך.

גם בהמשך נשארים אימות הענפים והמקורות, בדיקות הפריסה, שתי בדיקות
המשחקים והמסירות, גיבוי, migrate, בדיקות HTTPS והפעלת העובדים.
אם החלו מיגרציות או נפתחו כתיבות בהרצה קודמת שדורשת התאוששות,
הכלי מסרב להמשך אוטומטי ומפנה לקבלת הפריסה. הוא אינו משחזר מסד ישן.
אם אותם commits כבר נמצאים בפרודקשן תקין, מתקבלת הודעה שהגרסה כבר
פרוסה בלי בנייה, push או פריסה חוזרים.

להרצה מלאה מהתחלה, תוך שימור כל חסימות הפרודקשן:


אין צורך בו למסלול הרגיל, ואי אפשר לשלב אותו עם Fresh.

ל־12.10.2026 תחביר Python, קוד בדיקת ה־SSH ומפעילי PowerShell אומתו

### דרישות ותאימות

שומרים ועושים commit ידני בכל מאגר ששונה. בהפעלה הראשונה יש לעשות commit
גם לקובצי הכלי החדשים במאגר המשחק תחת `deploy/workspace/operations/`.
כל ארבעת המאגרים צריכים להיות נקיים, כולל קבצים חדשים שאינם מוחרגים.
אין stage, commit, reset, stash, force push או תיקון אוטומטי של קוד.

מתיקיית הפרויקט במחשב, כאשר Docker Desktop פועל עם Linux containers:

```powershell
& '.\PUBLISH_AND_DEPLOY.ps1'
```

המפעיל בשורש הוא קיצור מקומי. המפעיל שנשמר במאגר המשחק ניתן להרצה ישירה:

```powershell
& '.\Backgammon Game\deploy\workspace\operations\publish_and_deploy.ps1'
```

הכנה בלבד, בלי tests/build, רשת Git, SSH או פרסום:

```powershell
& '.\PUBLISH_AND_DEPLOY.ps1' -PreflightOnly
```

בדיקות ובנייה בלבד, בלי push או פריסה:

```powershell
& '.\PUBLISH_AND_DEPLOY.ps1' -ChecksOnly
```

נדרשים Python 3.12+, Node, pnpm, Git, Docker, SSH ו־SCP. המפעיל משתמש
ב־Python הקיים ובודק את גרסתו; אינו מתקין Python. סיסמאות SSH ו־sudo מוזנות
במסוף. Git משתמש בהרשאות הקיימות. אפשר להגדיר מראש מפתח SSH ואימות Git
כדי לצמצם הזנת סיסמאות; הסקריפט אינו משנה הרשאות או מנגנוני אימות.

החזיתות ובדיקות game-migrations/game-tests אינן חוזרות. אם קובצי בדיקות
הטורנירים השתנו, רק תמונת tournaments המקומית נבנית מחדש; יתר התמונות
נשמרות. נוצרים PostgreSQL/Redis זמניים חדשים, ואז נבדקים הטורנירים,
שירות הניתוח והקוביות. לבדיקות הטורנירים בלבד מוגדרים שלושה מפתחות חתימה
נפרדים וייעודיים; אין שימוש בסודות פרודקשן או שינוי סביבת בדיקות המשחק.
הקבלה החדשה שומרת ראיות למקורות, תמונות ושלבים שנשמרו, והמקורית אינה משתנה.
הבנייה ובדיקות השרת בזמן הפריסה ממשיכות להתבצע כרגיל.

ניתן להוסיף -PreflightOnly לאימות ההמשך בלבד, או -ChecksOnly ללא push ופריסה.
אם בדיקות הטורנירים נכשלות שוב, ניתן להשתמש באותו מזהה מקור לאחר תיקון
ו־commit, כל עוד השינויים נשארים בתוך ההיקף המותר ולא בוצע פרסום.

## מה מתבצע

1. בודק את ארבעת המאגרים, הענפים וה־origin של fetch ושל push. הענפים:
   `master` במשחק ובשני מאגרי הטורנירים; `main` בניתוחים. נשמרות ארבע גרסאות HEAD.
2. מריץ `pnpm install --frozen-lockfile`, את מלוא בדיקות Playwright של חזית
   המשחק ואת מלוא בדיקות Vitest של שתי חזיתות הטורנירים. Playwright מותקן
   אוטומטית עבור Chromium. מריץ `pnpm run build` בכל שלוש החזיתות.
3. מייצא את ארבעת ה־commits לתיקיית תוצרי ההרצה מתוך המאגרים הקיימים, בלי
   clone או worktree, ובונה שבע תמונות Linux/amd64 עם תג ייחודי ותוויות מקור.
   ההקשר כולל קוד Git בלבד; קובצי `.env`, מסדים ומדיה מקומיים אינם מקור הבנייה.
4. מריץ `makemigrations --check --dry-run` ואת כל בדיקות Django של שלושת
   השירותים בקונטיינרים עם PostgreSQL/Redis זמניים ורשת פנימית ללא גישה
   לפרודקשן. לפני game-tests מופעלת תמונת הקוביות שנבנתה באותה רשת פנימית,
   עם alias בשם release-dice וללא פורטים מפורסמים. ממתינים לתשובת /health
   ומגדירים DICE_SERVICE_URL=http://release-dice:4000. קונטיינר הקוביות נכלל
   בניקוי לפי תווית ההרצה גם בכשל מוכנות או בדיקות, מקומית ובשרת.
   דואר ותשלומים כבויים ואין סודות מקור. בדיקות Elixir של הקוביות
   מתבצעות בשלב Docker נפרד. כשל כלשהו עוצר לפני push.
5. מאמת שהקוד לא השתנה במהלך הבדיקות ושכל הענפים המרוחקים יכולים לקבל
   fast-forward. מבצע push לארבעת ה־commits המדויקים ומציג קישורי commit.
   אין אפשרות לבטל אטומית push בארבעה מאגרים; בכשל חלקי הקישורים נשמרים,
   ולא מתחילה פריסה. אין איפוס Git מרחוק.
6. מעלה חבילה עם הכלי, הגדרות הבדיקה והגרסאות ב־SCP ומאמת SHA256 לפני
   הפעלה. בשרת מאמת שהמעבר הראשוני לדוקר הצליח, את תמונות הפרודקשן
   והתצורה הפעילה, היעדר observer וכיבוי יחידות המקור הישנות. נועל פריסה
   מקבילה של כלי זה; כלי פריסה אחרים ושינויים ידניים עדיין דורשים תיאום.
7. מבצע `pull --ff-only` במאגרים הקיימים תחת `/home/dev/backgammon-project/sources`
   ומוודא שה־HEAD זהה לגרסה שנבדקה. קוד לא נקי או שינוי בענף מרוחק עוצרים
   את התהליך. אין החלפת תיקיות המאגרים או התקנת קוד מעל עריכות שרת.
8. בונה את התמונות בשרת עם הגבלת שני CPUs ו־3 GiB, ומריץ שוב את בדיקות Django
   במסדים זמניים. פלט הבדיקות והבנייה מוצג בזמן אמת. התמונות הישנות נשמרות.
9. מכין תצורת Compose פרטית המשנה רק תמונות. משווה את כל התצורה אחרי
   פענוח מחדש, לרבות מסדים, Redis, volumes, סודות, דגלי דואר, רשתות ופורטים.
   מריץ `check --deploy` לפני תחזוקה. מסרב להמשיך כשיש משחקים ממתינים/פעילים
   או משלוחי תוצאות שלא הסתיימו, כדי לא להיתקע בבדיקת health בזמן שהעובדים כבויים.
10. מאמת שוב שקונטיינרים ו־Nginx לא השתנו, חוסם את מסלולי Backgammon לציבור,
    עוצר את העובדים ומוודא שוב שאין משחקים פעילים, ואז עוצר את יישומי Backgammon.
    נגזר גיבוי חדש של שלושת מסדי הפרודקשן עם checksums ואימות קריאות dump,
    וכן עותקים של מדיה/static, Redis וסודות. זה אינו תרגול שחזור מלא של הגיבוי.
11. מריץ מיגרציות ו־collectstatic, מפעיל APIs/חזיתות/קוביות, בודק health ו־HTTPS
    דרך Nginx, מפעיל סט עובדים אחד ומאמת את מזהי התמונות ואת מצב הקונטיינרים.
    מחזיר את ניתוב הציבור ושומר קבלת `production_open` לפריסה הבאה.

אין ייבוא מחדש ממסדי המקור הישנים, איפוס נתוני ניתוחים, החלפת PostgreSQL/Redis
הפעילים, `down -v`, prune או ניקוי כולל. לא משנים אתרים אחרים או `shesh_besh_bot`.
תמונות ותיקיות תוצרי הרצות נשמרות; פינוי עתידי שלהן הוא פעולה נפרדת.
בדיקות אלה אינן בדיקת עומס/טורניר 32 שחקנים, מובייל, תשלום או Push למכשיר.

## במקרה תקלה

כל שלב מציג את שמו ואת נתיב הלוג, ומעביר stdout/stderr למסך. מוצגים
`FAILED STAGE`/`SERVER FAILED STAGE`, הודעת השגיאה ונתיב הקבלה.
פלט מקומי: `artifacts/auto-releases/<release-id>/`.
פלט שרת: `/home/dev/backgammon-project/reports/auto-releases/<release-id>/`.
הלוגים והתצורות הפרטיות בשרת מוגנים; אין להעתיק סודות לצ'אט.

כשל לפני תחזוקה אינו משנה שירותי פרודקשן. כשל אחרי תחזוקה ולפני מיגרציות
מנסה להחזיר את השירותים והניתוב הקודמים ללא שחזור מסד. מרגע שהתחילה
מיגרציה או שהופעלו עובדים חדשים, הכלי אינו חוזר אוטומטית למסדים או לקוד ישנים:
האתר עשוי להישאר בתחזוקה ומוצגת דרישת התאוששות. הקבלה חוסמת ניסיון נוסף
עד לטיפול. אין להחליף ידנית את `current.json` כדי לעקוף כשל.

## אימות הכלי

### שיפורי זמן ריצה — 12.10.2026

בדיקות Playwright המקומיות של המשחק רצות עם `--workers=2`. בשרת שנבדק
בפלט המשתמש יש 4 ליבות, 7.8 GiB RAM וכ־3.6 GiB זמינים לצד הפרודקשן,
ללא swap. עובד הבנייה מוגבל ל־2 CPUs ול־3 GiB RAM, עם
`max-parallelism=2`. שבע התמונות עדיין נבנות ברצף; זו מקביליות בתוך
BuildKit ואינה הפעלה של כמה בניות כבדות נפרדות.

`docker/configure_builder.py` משותף לכלי הפריסה ול־build_on_server.sh.
הוא ממחזר worker שכבר מתאים לפרופיל. לשדרוג worker ישן ועצור הוא משתמש
ב־`buildx rm --keep-state`, יוצר שוב את אותו שם ו־node, ומאמת שזהות volume
ה־cache נשמרה. worker ישן שעדיין רץ או בעל תצורה אחרת אינו משתנה.
אין prune, מחיקת cache או שינוי במשאבי מכולות הפרודקשן.
[תיעוד Docker לשימור cache](https://docs.docker.com/build/builders/drivers/docker-container/#cache-persistence).

תוויות SOURCE_REVISION ו־RELEASE_TAG הועברו לסוף שלבי הייצור בתמונות
הניתוח, הקוביות והחזיתות. כך שינוי מזהה הרצה בלבד אינו מבטל שכבות של
חבילות מערכת, העתקת נכסים או תיקוני הרשאות. ייתכן שבנייה ראשונה לאחר
שינוי סדר השכבות תידרש מחדש; את השיפור יש למדוד בהרצות הבאות.

כל שלב שהסתיים מציג את משכו ושומר אותו ב־`timings.json` לצד הקבלה,
כולל שלב שנכשל עם קוד יציאה. תחביר ותקינות סטטית עברו. בפלט המשתמש
מ־12.10.2026 עברו 8 בדיקות builder עם Docker מדומה ו־46 בדיקות כלי הפריסה,
כולל פענוח Compose אמיתי ללא הפעלת שירותים. אין עדיין מדידת שיפור
או הוכחת שימור cache בשרת לאחר השדרוג.

מיגרציות פרודקשן ממשיכות להשתמש ב־`migrate --noinput`, שמחיל רק מיגרציות
שטרם בוצעו. מסדי הבדיקות הזמניים נוצרים מחדש בכוונה. התקנת pnpm המקומית
נשארת עם `--frozen-lockfile`: בלוגים שנבדקו היא החזירה `Already up to date`
בתוך כ־0.7–1.6 שניות. שכבות Docker של תלויות שלא השתנו משתמשות ב־cache;
אין צורך להסיר את אימות התלויות או את בדיקות המיגרציות.

בדיקות שדרוג ה־builder משתמשות ב־Docker מדומה ואינן משנות מכולות או volumes:

```powershell
python -m unittest discover -s '.\Backgammon Game\deploy\workspace\docker' -p 'test_configure_builder.py' -v
```
