# בדיקת טורניר מקומית מקצה לקצה

הגרסה הנוכחית תומכת ב־16 או 32 שחקנים, ללא מגבלת זמן לתרחיש.
ראו [הרצת 32 שחקנים](LOCAL_32_PLAYERS.he.md): `-Players 32 -Headed`.
במצב הרגיל אין עיכובי כניסה או רענון יזומים; מוסיפים `-RecoveryChecks`
כדי להפעיל את תרחישי ההתאוששות בנפרד.
ברירת המחדל החדשה משתמשת ב־PostgreSQL המקומי וב־production build דרך
Nginx. ראו [הוראות PostgreSQL והשוואה לשרת](LOCAL_16_PLAYERS.he.md).
גרסת 32 השחקנים וההמתנה לאירועים הוכנה ולא הורצה בידי העוזר.
Nginx הוכן בתיקיית tools בפרויקט ומזוהה אוטומטית.
הצלחה כוללת גם [ספי ביצועים מפורשים](PERFORMANCE.he.md), לא רק סיום הטורניר.
תזמון העובדים הותאם ל־Docker: מרווח חמש שניות ומנות של עד 50 משימות.
להרצת tests, build ו־E2E בפקודה אחת עם דוח אחד ראו
[אימות תיקוני העומס וההתאוששות](REPAIR_VALIDATION.he.md).
תוצאת שמונת השחקנים המתוארת להלן היא ראיה היסטורית לגרסה שנבדקה אז.

ב־5 באוקטובר 2026 **הבדיקה המעודכנת עברה** בהרצה שביצע המשתמש (`20261005T124619-e4be49ae-report.zip`): שמונת השחקנים שלחו בקשות כניסה בתוך 25 אלפיות השנייה, שבעה משחקים הסתיימו באופן טבעי, שבע תוצאות חתומות נמסרו ופרס של 100 חולק פעם אחת. נבדקו גם כניסה מאוחרת של השחקן השני, כניסה חוזרת לאותו חדר והתחלת חצי גמר בזמן שרבע גמר אחר טרם הסתיים. לא נרשמו נעילות במסד, שגיאות שרת בתהליך הליבה או שגיאות דף בדפדפן. זו הוכחה לתרחיש המקומי של שמונה שחקנים; היא אינה בדיקת עומס של 32 שחקנים או אימות שרת הייצור, מכשירים פיזיים ופוש אמיתי. הבדיקות וההרצה בוצעו בידי המשתמש; העוזר בדק את הדוח ולא הריץ בדיקות או build.

## הרצה אחת ודוח אחד

ב־PowerShell:

```powershell
& 'C:\Users\User\Desktop\projects\backgammon\docs\tournament-e2e\run-tournament-e2e.ps1' -Headed
```

`-Headed` מציג את הדפדפן; אפשר להסיר אותו להרצה ללא חלונות דפדפן. ברירת המחדל היא Chrome המותקן במחשב. ל־Edge:

```powershell
& 'C:\Users\User\Desktop\projects\backgammon\docs\tournament-e2e\run-tournament-e2e.ps1' -Browser msedge -Headed
```

בסיום יוצג `SEND THIS FILE:` עם נתיב לקובץ `runs\<run>-report.zip`. שלח את ה־ZIP הזה; יש בו `report.txt`, סיכומים, אירועי הדפדפן ולוגים שנוקו מכרטיסי כניסה ומפתחות. אל תשלח את תיקיית ההרצה כולה: היא מכילה מסדי בדיקה ומפתחות זמניים.

אין מגבלת זמן לתרחיש או להמתנה להתקדמות המשחקים. שעוני המוצר נשארים פעילים. המשחקים משתמשים בקוביות אמיתיות ולכן זמן ההרצה משתנה. כישלון מפורש נשמר בדוח ואין ניסיון חוזר אוטומטי שמסתיר אותו. כל הרצה חדשה יוצרת סביבה חדשה; Ctrl+C עוצר אותה.

## מה נבדק

1. יצירת 16 חשבונות והתחברות והרשמה דרך ממשק הטורנירים; לכל שחקן סשן דפדפן נפרד.
2. טורניר נוקאאוט עם שעת התחלה: שמונה משחקים בסיבוב הראשון, ארבעה רבעי גמר, שני חצאי גמר וגמר.
3. שחרור 16 קליקים מכניסה משותפת ומדידת בקשות POST אמיתיות, בהפרש עד חמש שניות. שחקן שני מעוכב מעבר לחלון טריות המוכנות, ללא המצאת תשובה מוצלחת.
4. רענון וחזרה לאותו חדר ולאותו מושב.
5. 15 משחקים אמיתיים עד הוצאת האבן האחרונה, באמצעות פעולות חוקיות ב־WebSocket. אין הזרקת לוח, ציונים או תוצאות מנהל.
6. כניסה לסיבוב הבא ברגע שלזוג יש יריב, גם אם ענף אחר ממתין. `earlySemifinalObserved` מדווח אם סדר הסיומים כיסה חצי גמר מוקדם בריצה הזאת; ערך `false` אינו הוכחה לכיסוי.
7. התאמת תוצאות חתומות לחדר, למושבים, לציונים ולמנצח; התקדמות, פודיום ופרס יחיד של 100. לאחר הסיום נשלחות 30 מסירות כפולות ונבדק שוב שאין פרס נוסף.
8. בדיקת מסדים בקריאה בלבד: שני צבעים, 15 סיומים טבעיים, 15 תוצאות שנמסרו ו־15 משחקים שאושרו אוטומטית. נבדקים גם נעילות, שגיאות ליבה ובריאות המשימות לפני עצירת העובדים.

Vue, React, Django/Daphne, שירות קוביות ב־Elixir, Redis ועובדי המשימות הקיימים פועלים בפועל. יעד המשחק הוא נקודה אחת והכפלות כבויות. דוח הביצועים מפריד ACK, המתנה לעובד, SQL, שמירה ו־commit; המדידות האיטיות במסד נאספות מעל סף.

## מה נדרש במחשב

- Windows ו־PowerShell, Node התואם לגרסאות Vite המותקנות בפרויקט, Chrome או Edge.
- התלויות הקיימות מותקנות בשני הממשקים, כולל `@playwright/test` בממשק המשחק. הסקריפט אינו מתקין חבילות או דפדפן.
- סביבות Python של שני השרתים עם התלויות שלהן, כולל `cryptography`, `channels_redis` ו־Daphne. ברירת המחדל היא `.venv\Scripts\python.exe`; לשרת הטורנירים יש גם חיפוש ב־`venv`.
- Redis או Memurai מותקן. הסקריפט מפעיל מופע חדש עם קובץ הגדרות נפרד; הוא אינו משתמש בשירות Redis הרגיל.
- Elixir/Erlang ו־`mix` ב־PATH, עם תלויות שירות הקוביות מוכנות. `mix run` עשוי לקמפל את שירות הקוביות המקומי. הממשקים נבנים ל־production ומוגשים דרך Nginx מקומי.
- PostgreSQL המקומי פעיל בפורט 55432, דרייבר `psycopg2` בשתי סביבות Python ו־Nginx מותקן. שום כלי אינו מותקן אוטומטית. אין מעבר אוטומטי ל־SQLite או Vite כאשר חסרה תלות.
- הפורטים `18805`, `18806`, `18573`, `18574`, `18679`, `18807` פנויים. אם פורט תפוס ההכנה נעצרת, בלי לעצור את התהליך הקיים.

אפשר לבחור סביבות קיימות במפורש:

```powershell
& 'C:\Users\User\Desktop\projects\backgammon\docs\tournament-e2e\run-tournament-e2e.ps1' `
  -GamePython 'C:\path\to\game\.venv\Scripts\python.exe' `
  -TournamentPython 'C:\path\to\tournaments\.venv\Scripts\python.exe' `
  -RedisExecutable 'C:\path\to\redis-server.exe' `
  -NginxExecutable 'C:\path\to\nginx.exe' `
  -Headed
```

ההרצה מיועדת למחשב המקומי ב־Windows. אין להפעיל את כלי ההרצה הזה בשרת הייצור.

## בידוד הנתונים

לכל הרצה נוצרות תיקייה ושני מסדי PostgreSQL חדשים באשכול המקומי, עם משתמשים מוגבלים ושמות ייחודיים להרצה. רק מסדי ההרצה מקבלים מיגרציות ונתוני בדיקה; נתוני העבודה נשמרים. קובצי `.env` הרגילים אינם נטענים בשרתי הבדיקה. המסדים נשארים לצורך אבחון. לפרופיל SQLite/Vite הישן מוסיפים במפורש `-Database sqlite -UiMode dev`.

השרתים משתמשים ב־`DEBUG=False`, בבדיקות ההגדרות הרגילות, בתעודת HTTPS מקומית שנוצרת להרצה ובמפתחות חתימה חדשים. התעודה אינה מותקנת במאגר האמון של Windows. הגנות ההרצה מגבילות את שרתי Python למסדי הבדיקה ולפורטים המקומיים שהוקצו. בקשות הדפדפן מוגבלות לשני ממשקי הבדיקה המקומיים.

בסיום נעצרים רק עצי התהליכים שהסקריפט עצמו הפעיל. מכיוון שסיום תהליך ב־Windows עשוי להשאיר משימה באמצע עיבוד, בריאות העובדים נשמרת **לפני** העצירה. מצב `running` שנשאר במסד הבדיקה אחרי עצירת עובד מופיע בדוח ואינו לבדו מוכיח כשל. משימות במצב כשל/חסימה או עם שגיאת ניסיון שלא נוקתה מכשילות את הבדיקה. משימות מחזוריות עתידיות אינן נדרשות להיעלם מהתור.

## מה מעבר מוצלח מוכיח ומה עדיין חסר

`Passed: true` בריצה חדשה מוכיח שהגרסה המקומית השלימה את **התרחיש הזה** עם 16 שחקנים, כולל כניסה, 15 משחקים, התקדמות, מסירת תוצאות חוזרת ופרס יחיד, בלי הכשלים שהתרחיש מנטר. הוא אינו התחייבות שלא ייתכנו תקלות בתרחישים אחרים.

לפני טורניר אמיתי עדיין נדרשות בדיקת עומס במספר השחקנים הצפוי, בדיקה בסביבת השרת באותה גרסה והגדרות, ובדיקת שני שחקנים במכשירים אמיתיים. ההרצה המקומית אינה מכסה Nginx, עומס של 32 שחקנים, רשת סלולרית, מחוות גרירה/לחיצה בלוח, הכפלות, משחקי יעד ארוכים, דילוגי אי־הופעה או קריסת שירות באמצע משחק.

פוש, דואר, תשלומים, AI ושירות ניתוח המשחקים מושבתים בסביבה הזאת. בקשת הניתוח האמיתית שאחרי משחק עשויה להחזיר `503`; רק תגובה זו במסלול הניתוח המושבת נשמרת בנפרד ואינה נחשבת לכשל במסלולי הטורניר. אין להציג מעבר של הבדיקה כהוכחה שהאינטגרציות האלה עובדות.
