# צפייה בדוקרב בטורניר — עד שני צופים

עדכון תצוגה 28.10.2026: לבקשת המשתמש השעונים במסך הצפייה מוצגים אחד מעל השני, עם ההשהיה ביניהם ושמות גלויים. הרכיב המשותף קיבל מצב `stacked`, המופעל בצפייה בלבד. TypeScript ו־ESLint עברו; צילומי מחשב וטלפון אופקי מאשרים שאין גלילה במסילה. [תמונות וראיות](../../artifacts/tournament-spectator-stacked-clocks-20261028/README.md).

28.10.2026. אושר במפורש בשיחה: „מאשר, תבצע לפי התכנון עם מגבלה של שני צופים לכל דוקרב בטורניר.” המימוש מקומי; אין כאן אישור פריסה או ראיה שהשירות החי עודכן.

## התנהגות

- בעץ טורניר פעיל ומפורסם מופיע כפתור צפייה בדוקרב שכבר מתנהל. שני השחקנים משתמשים בכניסת המשחק שלהם ואינם נכללים במכסת הצופים.
- המכסה היא שני חיבורי צפייה לכל חדר דוקרב, לאורך כל המשחקונים שלו. כל כרטיסייה צורכת מקום, גם מאותו חשבון. אין תור המתנה אוטומטי.
- הצופה השלישי מקבל הודעה מתורגמת: „יש כבר שני צופים במשחק. אפשר לנסות שוב בהמשך.” אפשר לנסות שוב ידנית.
- משתמש מחובר רשאי לבקש הרשאה לצפייה. טורניר לא מפורסם/לא פעיל, דוקרב שהסתיים/ממתין להכרעה, וחדר שאינו משחק אינם נפתחים לצפייה. משתתף בדוקרב אינו נכנס לצפייה במשחק של עצמו.
- צפייה מציגה לוח, שמות, ניקוד, קוביות, קוביית הכפלה ושעונים; ללא פעולות משחק או טעינת יתרות ופרטי חשבון. מסך הצפייה אינו מרכיב את `GameProvider` ואינו משנה את סשן השחקן.
- במהלך חיבור מחדש הלוח נשאר מוצג עם הודעת ניתוק. בסיום הדוקרב נשארת תמונת הסיום והמקום משתחרר. סיום משחקון ביניים אינו סוגר את הצפייה.

## אכיפה וחיבור

1. שרת הטורנירים מקבל `POST /api/gamelink/fixture/<id>/watch/` עם אימות המשתמש והגנת CSRF. הוא בודק זכאות ומנפיק הרשאת צפייה נפרדת, המוגבלת לחדר/טורניר/דוקרב ולזהות המשתמש.
2. ההרשאה חתומה עם salt ייעודי `gamelink.spectator.v1`, ותקפה ל־120 שניות. היא אינה כרטיס שחקן ואין בה מושב. הקישור מחזיק אותה ב־fragment; הממשק מסיר אותו מהכתובת ושומר עותק ב־sessionStorage של אותה כרטיסייה, בנפרד מהרשאות המשחק.
3. `SpectatorConsumer` נפרד מקבל `/ws/watch/<room>/`. ההרשאה נשלחת במסגרת הראשונה, בתוך עשר שניות, ולא ב־query string של ה־WebSocket. השרת מאמת אותה ואת החדר הקיים; אינו יוצר חדר או מושב.
4. סקריפט Redis אטומי מנקה מקומות שפגו, בודק מכסה ותופס מקום עם מזהה חיבור ייחודי. כל תהליכי שרת המשחק משתמשים באותו מפתח לכל חדר ובאותו שרת Redis ראשון שהוגדר ב־Channels. אין ספירה מקומית נפרדת לכל worker.
5. הצופה שולח אות חיים מדי 15 שניות; ההקצאה תקפה ל־45 שניות ומתחדשת רק כשהבעלות קיימת. השרת מחדש גם את הרשאת החיבור הקצרה. ניתוק משחרר רק את מזהה החיבור שלו; ניתוק ישן אינו מוחק חיבור חדש. בניתוק פתאומי המקום יכול להישאר תפוס עד פקיעת ההקצאה.
6. בעלות שפגה או כשל Redis מפסיקים את הצפייה. נבדקת בעלות גם לפני שידור אירועים. כשל בתשתית הספירה אינו מאפשר לעקוף את המכסה; מצב Channels בזיכרון בלבד אינו פותח צפייה.
7. הלקוח רשאי לשלוח רק אימות ואות חיים. כל הודעת משחק אחרת מסורבת בשרת. אין קריאה למנגנוני נוכחות השחקנים, הטלות אוטומטיות, כניעה או הכרעות ניתוק.

## עומס והתאוששות

- השרת משתמש באירועי השידור הקיימים, עם רשימת שדות ציבוריים מפורשת. היסטוריית ביטולים, תמלילים, זריקות פתיחה פנימיות ושדות פרטיים אינם נשלחים לצופים.
- אין קריאה למסד לכל צופה בכל מהלך, ואין שידור שעון מדי שנייה. תצוגת השעון משתמשת בעוגן הזמן המוסמך ובמנגנון התצוגה הקיים.
- פעם בדקה לכל צופה פעיל מתבצעת קריאה קטנה של מצב החדר, גרסה וניקוד. רק אם יש פער נטען צילום ציבורי מחדש. כך ניתן להתאושש גם מאירוע סיום שאבד בשידור. זו קריאה מוגבלת בזמן, ולא polling של מצב המשחק בכל מהלך.
- גרסאות ישנות אינן מחזירות את הלוח אחורה. צילום בעל אותה גרסה יכול לעדכן ניקוד בסיום משחקון.
- ההגבלה היא לכל דוקרב, ולא לכל השירות. לא נמדדה קיבולת שירות או השפעת צופים על זמן מסירת מהלך.

## הגדרות

נדרשים הגדרות GameLink ו־Redis הקיימים. אין migration ואין ספרייה חדשה.

הכתובת לממשק המשחק נגזרת כברירת מחדל מה־origin של `GAMELINK_BACKGAMMON_URL` עם `/6b/backgammon`. אפשר להגדיר בשרת הטורנירים `GAMELINK_GAME_FRONTEND_URL` לבסיס SPA אחר; כאשר קיים `GAMELINK_FRONTEND_URL` בסביבה הוא משמש גם כברירת המחדל. לתצורת Docker הקנונית הקיימת אין צורך בערך נוסף. סביבת פיתוח עם React בפורט נפרד צריכה את הכתובת המלאה לבסיס הממשק, למשל `http://localhost:5173/6b/backgammon`.

## אימות שבוצע

- TypeScript מלא בחזית המשחק; TypeScript של היישום ושל הבדיקות בחזית המועדון — עברו.
- ESLint בקובצי המימוש והבדיקות החדשים ובקובצי הממשק ששונו — ללא שגיאות. בחזית המשחק יש שתי אזהרות Fast Refresh קיימות על הייצוא הקיים ב־`router.tsx`.
- Stylelint בקומפוננטות Vue ששונו — עבר.
- ניתוח תחביר AST של תשעת קובצי Python שנוספו/שונו — עבר.
- סקירה סטטית נפרדת של חוזה ההרשאות, אירועי המשחק/סיום, המכסה וחיבורי הממשק — בוצעה; תוקנו כפילות הודעה והתאוששות מאירוע אבוד.
- נכתבו בדיקות שרת, Lua מול Redis ייעודי, כרטיס צפייה, ניווט מאוחר/החלפת זהות, מצב צפייה בלבד, עדכוני ניקוד, חיבור מחדש וסיום. **הבדיקות לא הורצו.**
- **tests, build, דפדפן, מובייל, Redis חי ובדיקת עומס לא הורצו**, בהתאם לחלוקת הבדיקות בפרויקט. אין commit, push או פריסה. ניסיון קריאת Git של מאגר המשחק נכשל בגלל מטא־נתוני worktree קיימים שאינם נפתרים בסביבת ההרצה; לא שונו מטא־נתוני Git.

יש להריץ בסביבות הפרויקט הקיימות:

```powershell
Set-Location 'C:\Users\User\Desktop\projects\backgammon\Backgammon Game\backend'

Set-Location 'C:\Users\User\Desktop\projects\backgammon\backgammon-tournaments-backend\tournaments'

Set-Location 'C:\Users\User\Desktop\projects\backgammon\Backgammon Game\frontend'

Set-Location 'C:\Users\User\Desktop\projects\backgammon\backgammon-tournaments'
```

בדיקת הספירה האמיתית מול Redis מדולגת כברירת מחדל. כדי להריץ אותה יש להגדיר במפורש `SPECTATOR_TEST_REDIS_URL` לשרת Redis המיועד לבדיקות ולחזור על פקודת בדיקות שרת המשחק. הבדיקה משתמשת במפתח חדר אקראי ומסירה את המפתח שלה בלבד; אינה משתמשת אוטומטית בכתובת Redis של השירות.

אימות ידני במחשב ובמובייל: להפעיל דוקרב בטורניר עם שני משתתפים, להיכנס משני חיבורי צפייה נוספים, ולוודא ששלישי נדחה; לצאת מאחד ולפתוח את השלישי; לבדוק ניתוק פתאומי ושחרור אחרי 45 שניות, רענון, המשך בין משחקונים, ניקוד וסיום. יש לוודא שאין פקדי משחק לצופים, שהשחקנים ממשיכים לשחק כרגיל, ושכל הטקסטים בעברית ובאנגלית קריאים ואינם נחתכים.
